# 工程模式 v1.0 · 已有项目迭代维护 (v4.4.0)
> OneMaker Pipeline v4.4.0 | 自包含模块，不加载 agent_core.md 完整规章 | 路由入口定义于 agent_core.md §项目路由分叉
> 自包含模块 + 项目类型适配（不加载 agent_core 完整规章）

## 触发

进目录 → 读取 `memory/_index.json` → 匹配到已有项目（pipeline_completed=true 或 status=completed）
→ 读取 `memory/projects/{name}.json` → 加载本文件 → 进入 6 步循环

> 新项目仍走 12 角色管线（agent_core.md）。工程模式不加载 agent_core.md。

## 核心约束（自包含，不依赖 agent_core.md）

### 🔴 硬约束
- **⑥记忆写入不可跳过**：每次迭代结束→更新 project memory + session log
- **Bash 验证必须含 EXIT_CODE 指纹**：`echo "EXIT:$?"` 结尾，无 EXIT 字样→无效
- **修改后必须验证**，验证失败→修复→重试（最多 3 轮）→仍失败→回退+报告
- **记忆写入前 4 问自检**：①下次用得到？②不能推导？③没写过？④不超限？
- **项目文档脱敏**：产出中禁止出现"管线/pipeline/R1-R12/Bash验证/CTO审查/quality_gate"等内部术语

### 🟡 执行约束
- ③依赖分析不通过→不可进入④修改（修复依赖问题后才能改）
- ⑥用户通知必须是人读摘要，非技术日志
- 涉及多文件修改→必须先读 project memory 了解项目架构
- 视觉改动 >1 文件 → 必须调起 R3 视觉创意总监重新出走查

## 6 步迭代循环

| 步骤 | 触发条件 | 跳过条件 | 产出 |
|------|---------|---------|------|
| ① 健康检查 | **每次** | — | 项目健康摘要 ≤3 行 |
| ② 状态快照 | 涉及文件修改 | 纯查询/纯讨论 | 变更前文件清单 ± git diff |
| ③ 依赖分析 | 修改 >1 文件 或 核心模块 | 独立文件 且 无 import 依赖 | 受影响模块清单 + 风险等级 |
| ④ 修改 | 有修改需求 | — | 代码变更 + Bash `EXIT:0` |
| ⑤ 回归验证 | 修改 >3 文件 或 核心模块 | 文案/注释/配置修改 | 测试/手动验证结果 |
| ⑥ 通知+记忆 | **每次** | — | 用户摘要 + memory 更新 |

### ① 健康检查
```
- git status → 未提交变更？有 → 标注风险
- 读取 project memory → 上次遗留阻塞项？
- 项目有 backend/ → curl health check（若运行中）
- 项目有 frontend/ → curl 关键页面 200 OK
- 检查 .env / config 文件是否有异常变更
```

### ② 状态快照
```
- 列出将修改的文件清单
- git diff HEAD（若有 git）
- 记录当前版本/commit hash
- 备份关键配置文件的当前状态
```

### ③ 依赖分析
```
- grep -r "被修改函数名/类名/变量" → 列出所有引用位置
- 标注：直接依赖 / 间接依赖 / 无依赖
- 变更风险评估：
  🔴 高风险：核心模块(backend/main.py, frontend/App.jsx 等)
  🟡 中风险：多处引用的工具函数/组件
  🟢 低风险：独立文件/纯样式文件
- 识别跨模块依赖链（如 backend API 变更 → frontend 调用方需要同步更新）
```

### ④ 修改
```
- Claude 原生能力：读代码→分析→定位→Edit
- 遵循项目现有代码风格和架构约定
- 所有代码修改 → Bash 验证产物 + EXIT_CODE 指纹
- 修改范围必须与③依赖分析结果一致
```

### ⑤ 回归验证
```
- 运行现有测试：pytest / npm test / 手动验证（按项目类型适配）
- curl 验证关键端点（若适用）
- 验证③中识别的依赖模块未被破坏
- 验证结果：✅通过 / ⚠️部分通过 / ❌阻断
- ❌阻断 → 回退修改 → 报告 → 不写入记忆
```

### ⑥ 用户通知 + 记忆写入
```
用户侧输出：
  - 修改摘要（人读，≤5 条变更）
  - 验证结果
  - 遗留风险（若有）

记忆写入（通过 4 问自检后）：
  - memory/projects/{name}.json：更新 notes / artifacts / cto_reviews(若有)
  - memory/sessions/{date}.json：追加本次迭代记录
```

## 项目类型适配

| 项目类型 | ①额外检查 | ③重点关注 | ⑤验证方式 |
|---------|---------|---------|---------|
| public | frontend 页面可达 + SEO | frontend/ ↔ backend/ 接口契约 | pytest + curl 关键页面 |
| internal | backend/ 健康检查 | 适配器 ↔ 引擎接口 | 端到端自动化流程 |
| poc | 核心功能可演示 | 演示路径完整性 | 手动核心流程 |
| personal | 可运行即可 | 单模块依赖 | 启动+核心功能 |

## 迭代风险对照（6 类，每次③步骤对照检查）

| 风险 | 检查方式 | 预防步骤 |
|------|---------|:---:|
| ①改前不查依赖 | grep 引用位置 | ③ |
| ②改后不回测 | 运行测试/curl 验证 | ⑤ |
| ③状态不一致 | git status + memory 对照 | ②⑥ |
| ④无声断裂 | ③识别的依赖模块逐一验证 | ⑤ |
| ⑤配置漂移 | .env / config 文件对比快照 | ②⑤ |
| ⑥用户无感知 | ⑥人读摘要输出 | ⑥ |

## 反模式自动检测（每次①步骤检查）

| 反模式 | 检测方法 | 预防 |
|--------|---------|------|
| CSS 同名覆盖 | `grep -rn "相同选择器" frontend/*.css` | 检查是否有同名选择器 |
| 数据库幽灵库 | `grep "相对路径" backend/*.py` | 检查 DB 路径是否为绝对路径 |
| 重启删库 | `grep "rm.*\.db"` 启动脚本 | 禁止启动脚本中删除数据库 |
| 缓存欺骗 | 检查 Service Worker / 版本号 | 提醒 bump 版本号 |
| 自说自话改视觉 | 检查是否绕过了 R3 | 视觉改动>1文件→强制调R3 |

## 断点恢复

```
下次进入工程模式时：
  1. 读取 memory/projects/{name}.json → notes 字段
  2. 若有 pending_action → 展示上次断点 + 待办
  3. 若无 → 正常 6 步循环从 ① 开始
```
