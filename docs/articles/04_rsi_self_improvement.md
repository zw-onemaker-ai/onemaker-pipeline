# RSI（递归式自我改进）实战：给 AI 管线装上「错误登记册」

做过工程的人都知道一个残酷的事实：**修 bug 是简单的，记住"别重犯"才是难的。**

尤其是现在，你的"团队"里有一堆 AI Agent 在跑管线。它们翻车翻得很有创意——你刚修好的问题，过几天换个姿势又从另一个角落冒出来。不是能力问题，是记忆问题：修过的坑，没有任何机制保证它不再犯。

前几天我给自己的 AI 交付管线加了一套机制，叫 **RSI（递归式自我改进）**。核心只有一句话：

> **每一条失误，都必须变成一条"以后会自己报警"的检查。**

一周不到，登记册里已经有 5 条记录，3 条完成验证归档。下面把这套机制的设计、两个真实案例、和它跑出来的效果，完整拆给你看。

## RSI 是什么：从「智能爆炸」到一本错题册

**Recursive Self-Improvement（递归式自我改进）**——这是 AI 领域一个有点年头的概念。1965 年 I.J. Good 提出"智能爆炸"猜想：一台超级智能机器，能设计出更好的机器。到今天，从 Gödel Machine 到 Darwin Gödel Machine、SICA 这一批自我改进 Agent 研究，本质上都在回答同一个问题：**能不能把"改进自己"做成一个持续转动的循环？**

而这些研究里有一条最重要的共识：**自我改进的瓶颈不是"改写自己"这个动作，而是"评估"。** 怎么知道改完是变好了还是变坏了？没有可靠评估器的自我改进，约等于自毁。

我把这个概念缩小了一个数量级，落到自己的管线上：

- **不改进模型，不改进代码——只改进管线自己的工作制度**：规则、闸门、记忆；
- **评估器 = 能跑的闸门 + 固定打卡 + 连续两次通过**——改进成不成立，不靠感觉，靠检查结果；
- **递归的骨架一点没少**：改进流程的机制，自己也走这套流程；机制自己出的 bug 也进登记册；连"闸门的实现规范"都被注册成闸门——后面案例二讲的就是这个。

一句话：前沿实验室在研究"模型改进模型"，我先让"流程改进流程"。

## 为什么"记住就好"是废话

先说痛点。管线跑起来之后，失误基本有三种死法：

1. **修了就忘。** 同一个坑，换个形态再犯一次；
2. **根因挖不深。** 只修现象："重启一下好了"——然后每周重启一次；
3. **假完成。** 检查项躺在"已完成"里，但没有人在验证它是不是真的完成了。

我以前的解法是写一份"经验教训.md"。结局是：写的时候很感动，之后再也没打开过。

所以新机制的第一条硬规矩就是：**没有可执行的检查命令，就不算修正完成。**

## 四步闭环：登记 → 修正 → 验证 → 归档

机制流程很土，但每一步都有硬要求。

**① 登记（下班时）**——每条失误记录四个字段：

- **症状**：发生了什么（写现象，不写解释）
- **根因（至少挖两层）**：现象 → 直接原因 → 系统原因
- **修正**：改了什么，改在哪
- **预防闸门**：一条**能跑的检查命令**——以后如果再犯，它自动报警

**② 修正**——当天或次日第一件事处理。紧急的当场登记、当场修。

**③ 验证（上班打卡时）**——一个 `rsi_check.sh` 脚本，把所有闸门全量跑一遍，全绿才开工。注意：**验证只在这个固定时点执行**——随时随地的"我检查过了"，等于没检查。

**④ 归档**——连续两次验证通过才归档。同一根因第二次触发 → 强制升级为**流程条款**，而不是留在登记册里当"备忘"。

还有两个反直觉的设计：

- **死路也要记。** 不只是错误，"发现这条路走不通"也登记（比如"先怀疑调度器"就是一条死路）——下次直接跳过它。
- **黄金路径与错误同等重要。** 好不容易跑通的流程，登记成"下次直接复用"的路线。登记册只记坑是不够的，也要记路。

听起来像流程繁文缛节？看两个真实案例就知道，它逮到的是什么级别的坑。

## 案例一：幽灵双跑——"执行了两遍"的日志

某天巡检，发现定时任务的日志里，每一轮都有**字节级完全一致的两段**完整输出。

第一直觉：调度器双触发了？脚本被跑了两遍？

如果是你，会先查什么？我当时的冲动是直接去改 crontab 加锁。幸好停了一下，先做了三件事：

```bash
# ① cron 日志：确认调度器的真实触发次数 → 只有一次
# ② 对两段日志做字节级 diff   → 完全一致，连时间戳都一模一样
# ③ 审计写入路径              → 发现 log() 同时做了 print() + 直写文件
```

真相：`log()` 函数同时往 stdout 和日志文件写；而 cron 又把 stdout 重定向进了同一个文件。于是日志里出现两份内容——更阴的是，Python 的块缓冲让第二份**在进程退出时整块落盘**，伪装成"完整跑了两遍"。

根因分了三层：现象=日志重复 → 直接=写入路径双写 → 系统=写日志函数没有区分运行环境（终端 vs 重定向）。

修正只有一行：加 `sys.stdout.isatty()` 判断——终端才 print；重定向时，文件直写是唯一日志源。

然后是关键一步——**把它变成闸门**：

```bash
# 打卡时自动跑：防"日志双写"回归
grep -c 'isatty' job_daily.py    # 期望 ≥1
```

顺手，"日志疑似双跑"的排查路径被登记成了黄金路径：**cron 日志 → 字节 diff → 写入路径审计**。三件套先做，别先动调度器——那是一条死路。

## 案例二：给闸门做闸门——机制自己翻车了

这个案例我最喜欢，因为它是**建立当天**就发生的。

机制里有一类"完成标记"闸门：某件事在真正落地之前，应该一直显示"待验证"。结果建立当天它就报了假绿——**一件还没做的事，被读成了"已完成"。**

排查发现：这个闸门用了**自由文本子串匹配**——而"完成"这个字符串，出现在了一段描述"未来计划"的文本里。系统把"打算做"，读成了"已经做完"。

这是最讽刺的一类 bug：**你的检查机制本身，没有人在检查。**

修正：所有"完成标记"类闸门，一律锚定**结构化字段**（检查某个键是否存在），禁止裸文本匹配。而且——把这个规范本身也注册成了一条闸门，防止将来实现退回去。

"机制自身的缺陷也登记"，这条被写进了机制规则里。算是 **RSI 的 RSI**。

## 运行数据

机制上线后的头几天（发文时快照）：

| 项目 | 数值 |
|------|------|
| 登记条目 | 5 |
| 已归档（连续两次验证通过） | 3 |
| 验证队列中 | 2 |

有工程 bug，也有机制自身的缺陷。每天上班，闸门脚本自动全量跑一遍，全绿才开工。

最大的变化不是"错犯得少了"，而是：**每修一个坑，系统里就多一条"以后永远会跑"的检查。** 坑还是会有——但同一个坑，很难踩第二次了。

## 大概率会问的三个问题

**Q：一个人/小团队，值得搞这么一套吗？**

A：整套机制的成本就是"一个 md 文件 + 一个脚本 + 每天跑一次"。它拦下一次重复翻车，就把成本赚回来了。

**Q：会不会变成走形式？**

A：两条规则防形式主义：闸门必须能跑（写不出命令 = 没修完）；验证只在固定时点跑（随时糊弄不了）。

**Q：闸门越攒越多，跑不过来怎么办？**

A：闸门都是毫秒级的 grep / 断言，几十条也就一两秒。真正花时间的是"登记时把根因挖到第二层"——但这一步恰恰最值钱。

## 这套机制的参考来源

- **SRE 的无指责复盘**：对事不对人，是登记能持续的前提；
- **fail-to-pass**：修复必须配回归测试——和代码评测的思路同构；
- **Darwin Gödel Machine / SICA** 等自我改进 Agent 研究：共同点是"评估先行、只保留被验证的改进"。

但真正让它转起来的，是几条土规矩：闸门必须能跑、验证只在固定时点、连续两次才算数、同根因二次触发就升级流程。

## 上手建议（从零开始）

如果你想给自己（或你的 AI 管线）来一套：

1. **先建登记册**：一个 `lessons.md`，字段就四个：症状 / 根因 / 修正 / 闸门；
2. **写下第一条闸门**：把最近修过的一个 bug，翻译成一条能跑的命令；
3. **固定打卡时点**：每天开工第一分钟，全量跑一遍；
4. **连续两次才算数**：不给自己"改完就宣布胜利"的机会。
